## [v5.0.0] - 2026-09-03

This major release migrates to a new SDK major version and includes several
security- and correctness-driven behavior changes that can break existing
configurations; see Breaking below. No attributes were removed or renamed, but
`password_wo_version` is now required whenever `password_value` is configured,
and server-owned field metadata is no longer accepted as input.

### Breaking

Each item below can fail a `terraform plan`/`apply` that succeeded on v4.0.x.
One previously accepted input is now computed-only; the remaining items are
behavior changes. Pin `~> 4.0` to stay on the previous line.

- **Remote plaintext `http://` `server_url` is rejected at configure time.** tss-sdk-go v3.1.0's security engine refuses plaintext HTTP to a non-loopback host (it would expose the credential on the wire), and the provider now surfaces that at plan/apply with an error naming the opt-in. **Migration:** use `https://`, or — if you connect to a remote Secret Server behind upstream TLS termination and accept the risk — set `allow_insecure_http = true` (or `TSS_ALLOW_INSECURE_HTTP=true`). `http://` to loopback (`localhost`, `127.0.0.1`, `::1`) is unaffected.
- **Username/password authentication now probes the configured backend before sending credentials.** tss-sdk-go v3.1.0 distinguishes Secret Server from Delinea Platform with an unauthenticated `GET` to `<server_url>/api/v1/healthcheck` and then `<server_url>/health`; a healthy endpoint must return a direct 2xx response because redirects are deliberately not followed. **Migration:** permit the appropriate health path through any reverse proxy instead of routing only legacy `/healthcheck.aspx`. Static Secret Server token authentication skips the probe.
- **The multi-secret data source and ephemeral reads now fail the whole read if any requested id is missing or inaccessible.** v4.0.x warned and returned the remaining secrets; a shortened, positionally re-indexed list could silently feed the wrong value to a downstream consumer. `data.tss_secrets` and the `tss_secrets` ephemeral resource now abort with a diagnostic instead. **Migration:** remove ids that no longer exist from the `ids` list, or split reads so a deletable id is not fatal to the batch.
- **Provider connection attributes that are unknown at configure time now error instead of falling back to environment variables.** A value like `server_url = module.ss.url` before that module is applied previously used the operator's `TSS_*` env var at plan time (possibly a different server or identity) or produced a misleading "Server URL is required" error. **Migration:** set the attribute statically, use the `TSS_*` environment variable exclusively (leave the attribute unset), or stage the first apply with `-target` on the value's source.
- **Every `fields` block now requires `fieldname`, and the name must match exactly one field name or slug on the secret template.** v4.0.x accepted anonymous fields, while name/slug collisions could select the wrong field; both cases could become a silent no-op, an opaque server error, or a write to the wrong field. **Migration:** add the intended `fieldname`, delete blocks that reference fields no longer on the template, and remove ambiguous name/slug aliases from the template.
- **`sshkeyargs` is now replacement-only (ForceNew).** Secret Server generates SSH keys and passphrases only at creation, so changing the block now recreates the secret instead of silently recording settings that were never sent. **Migration:** expect a destroy/create in the plan when you change `sshkeyargs`; it was previously an in-place no-op.
- **`itemvalue` is rejected on password fields.** Terraform state never holds a password (the provider records an empty `itemvalue` for every field the template marks `IsPassword`), so a configured `itemvalue` on such a field could never match the value read back and every apply failed with Terraform's "Provider produced inconsistent result after apply" error. The provider now rejects the configuration before writing anything, with an error naming the migration. **Migration:** move the value to `password_value` together with `password_wo_version` (or set `generate = true`).
- **Managed-secret reads fail closed.** When Secret Server reports a managed secret as inaccessible during refresh — classic Secret Server's ambiguous HTTP 400 `API_AccessDenied`, or any HTTP 404 — the provider keeps the resource in state and errors instead of planning a replacement, because those responses cannot distinguish a deleted secret from missing permission or from an attachment download failing on a live secret. **Migration:** after confirming that a secret was deleted outside Terraform, run `terraform state rm` on the resource and apply again. Most providers drop a 404'd resource from state automatically; this one deliberately does not.
- **Stricter validation of password-field rotation inputs.** Empty `password_value` strings, `password_value` without `password_wo_version`, `password_wo_version` with no accompanying `password_value`/`generate` on a create or a new field, and `password_value` on a non-password template field are now rejected rather than silently accepted (the last case could round-trip a password into state via `itemvalue`). **Migration:** configure a non-empty `password_value` with `password_wo_version`, bump them together for later rotations, and keep `password_value` on password fields only.
- **Configured filenames must target file fields and use an SDK-preserved extension.** Secret Server changes an explicit empty filename to `File.txt`, and the SDK appends `.txt` unless the name ends in an extension containing only ASCII letters, digits, or underscores. The provider previously also ignored a filename placed on a non-file template field. Those behaviors can violate Terraform's plan/state consistency contract. **Migration:** configure the final filename with a supported extension such as `.pem`, `.txt`, or `.p12` only on a field the template marks as a file; otherwise omit `filename`.
- **`fileattachmentid` is now computed-only.** v4 declared this server-assigned identifier `Optional+Computed`, but neither the v2 nor v3 SDK uses it when writing a secret. Accepting it silently ignored the requested attachment and could then produce inconsistent state. **Migration:** remove `fileattachmentid` from `fields` blocks; provide new file content through `itemvalue` and `filename`, and let Secret Server return the attachment ID.
- **Template field metadata is now computed-only.** `isfile`, `isnotes`, `ispassword`, `islist`, and `listtype` describe the selected Secret Server template and are not write inputs. v4 accepted configured values even though request construction ignored them, and the secret response cannot round-trip `islist` or `listtype`, causing inconsistent post-apply state. **Migration:** remove these five attributes from `fields` blocks and let the provider derive available metadata from Secret Server.
- **The provider's Go module path moved from `github.com/DelineaXPM/terraform-provider-tss/v4` to `github.com/DelineaXPM/terraform-provider-tss/v5`.** This does not change how configurations reference the provider (`source = "DelineaXPM/tss"`), but Go programs that import or embed the provider must update their imports to `/v5`.

### Added

- Fake-server tests that run the provider through the real Terraform CLI (`resource.UnitTest`) for create, update, partial-create tainting, `tss_secret_deletion` success/refused/ambiguous outcomes, the data sources, both ephemeral resources, and provider URL validation; direct unit tests for the SSH-key plan modifier and for the v0→v1 state upgrader invoked through the framework. CI installs Terraform for these tests and validates every `examples/secrets/*` root module against a `dev_overrides` build.
- The live acceptance suite is now a reusable workflow shared by the release gate and the scheduled run. The release gate requires the `TSS_TEST_SSH_TEMPLATE_ID` and `TSS_TEST_MIXED_TEMPLATE_ID` repository variables and sets `TF_ACC_REQUIRE_ALL_TESTS`, so the SSH-key acceptance tests fail instead of skipping when a template id is missing.
- `terraform-provider-tss -version` prints the goreleaser-injected version and commit; `-debug` starts the provider in debug mode for attaching a debugger.
- CI now enforces two of this release's acceptance criteria on every push and pull request: a tidy-drift step (`go.mod`/`go.sum` must be exactly what `go mod tidy` produces) and a `govulncheck` job (symbol-level reachability scan; fails only on advisories reachable from this module).
- The `ci` workflow is hardened to match tss-sdk-go's: a `gofmt` gate, the race detector on the test step, `govulncheck` pinned via a tool directive in a separate `tools/go.mod` module — Renovate manages it like any Go dependency and its modules ride the setup-go cache (keyed on both go.sum files), while the scanner's module graph stays out of the provider's own dependency resolution, so a scanner bump can never change code linked into released binaries (`renovate.json`'s shared-preset reference now uses the `local>` form) — a concurrency group cancelling superseded PR runs, job timeouts, and setup-go caching kept on for the PR-facing jobs (disabled on the release and live-credential paths, where cache isolation matters). The `release` workflow now declares the `contents: write` permission it needs instead of inheriting the default token scope.
- The `release` workflow now gates publication (adopting tss-sdk-go's gate-before-publish model while keeping the GoReleaser + GPG Terraform Registry mechanism providers require): pushing a `v*` tag runs three required gates before GoReleaser — **verify** (the release tag's commit must be on `main` and named in `CHANGELOG.md`, plus `gofmt`/build/vet/race-test/tidy-drift), **dependency** (no active `go.mod` `replace` directives, `govulncheck`), and a **live acceptance** run against the `live-tests` environment (pinned Terraform 1.15.9) — so a bad tag cannot reach the public registry. GoReleaser runs under a new `release` environment restricted to `v*` tags.
- New `CodeQL` workflow (`security-extended` queries, PRs + weekly schedule, `build-mode: autobuild` — the deployed CodeQL CLI rejects `none` for Go), ported from tss-sdk-go.
- New `Live acceptance tests` workflow: weekly and on-demand `TF_ACC` run of the full acceptance suite against a live Secret Server, using a `live-tests` GitHub environment for credentials. Its serialized Terraform matrix gates the documented 1.11.0 floor and pinned 1.15.9 current version, while an allowed-to-fail latest-release canary provides early compatibility warning. Inert until the environment is provisioned. The environment may use either a bearer token or username/password credentials; token authentication takes precedence if both sets of secrets remain configured, and domain and insecure-HTTP settings are forwarded when configured.
- New optional `allow_insecure_http` Bool attribute on the provider block (env fallback `TSS_ALLOW_INSECURE_HTTP`), wired to the SDK's `Configuration.AllowInsecureHTTP`. Default `false` keeps the v3.1.0 plaintext-HTTP rejection for remote hosts; setting it `true` is a deliberate opt-in for setups such as TLS terminated upstream of Secret Server. Without this, a remote `http://` `server_url` would hard-fail with an error message naming an SDK option provider users cannot reach.

### Fixed

- The encrypted-state wrappers now select the provider version recorded in `.terraform.lock.hcl`. Terraform deliberately retains previously installed versions after `terraform init -upgrade`; those stale binaries no longer make every subsequent wrapper invocation fail with an unrecoverable multiple-provider error.
- Creating a secret without any `fields` blocks no longer adopts every template field into state during refresh, and configurations that name the same template field more than once (including by display name and slug) are rejected before any credential is written.
- **Updates no longer reset optional secret settings the configuration omits.** Whenever any attribute changed, the framework marked every unconfigured Optional+Computed setting unknown in the plan and the provider sent the resulting zero value in its PUT, so a rename or field change silently disabled checkout, comment requirements, permission inheritance, session recording, and similar settings and cleared `launcherconnectassecretid` and `checkoutintervalminutes` (the bug predates v4). Every such attribute now carries `UseStateForUnknown`, and `Update` falls back to prior state for anything still unknown, so the PUT carries the values Secret Server holds. Covered by a fake-server test that drives the real Terraform CLI and asserts on the PUT body.
- Optional secret settings have an explicit create contract: because tss-sdk-go's request type uses scalar fields, an omitted setting is encoded as `false`/`0` on create and the refreshed server response becomes computed state. Configure any non-zero creation policy explicitly; `active` separately defaults to `true`. Updates preserve omitted values as described above.
- Secret IDs and integer settings are range-checked before SDK calls against Secret Server's signed 32-bit API range. This prevents a large Terraform `Int64` from wrapping to another secret or setting on released 32-bit provider builds.
- The "password is set but username is missing" diagnostic is reported for that condition again; a `switch` ordering bug had collapsed it into the generic "Credentials missing" message.
- Provider authentication validation now also rejects a token combined with a password but no username; the combination previously slipped through despite the documented exactly-one authentication contract.
- `terraform-provider-tss` no longer panics on a single unexpected argument (`os.Args[2]` was read behind a `len(os.Args) >= 2` guard). The binary now accepts `-debug` and `-version`, prints usage for anything else, and the `encrypt`/`decrypt` state-file helper exits non-zero on failure — previously it logged and exited 0, so none of the error checks in `encryption_scripts/` could ever fire.
- `encryption_scripts/`: the Linux `init` and `destroy` wrappers invoked a misspelled `ffind` and so never found the provider; all wrappers now locate goreleaser-named binaries (`terraform-provider-tss_v*`) as well as a bare `terraform-provider-tss`, `destroy` gained the lock-file check the other wrappers had, `init` re-resolves the binary after installing it instead of exiting 1, and every wrapper honors a dedicated `TFSTATE_PASSPHRASE` before falling back to the legacy username+password derivation.
- `DecryptFile` validates the ciphertext length before slicing the salt and nonce instead of panicking on a truncated or foreign file. Encrypt and decrypt write through a file restricted to the current user: mode `0600` on Unix and a protected, current-user-only DACL on Windows, avoiding inherited directory permissions when the temporary file replaces the destination.
- State encryption replaces files through a synced, access-restricted temporary file before renaming it over the destination, preserving the prior state if a write fails. The final replacement is atomic on Unix; Windows uses the operating system's replace-in-place rename semantics. The Linux and Windows wrappers atomically acquire a lock directory rather than racing between an existence check and lock creation; Windows launchers delegate to a PowerShell `try`/`finally` implementation so state is re-encrypted after Terraform errors and terminal interruption.
- The encrypted-state `init` wrappers can bootstrap a missing or pre-v5 provider without asking Terraform to parse encrypted state: under the state lock they temporarily stage the ciphertext, run a backend-disabled provider install, restore and decrypt the state, then run the requested init. Provider-installation options such as `-plugin-dir` and `-upgrade` reach the bootstrap. The wrappers reject `-from-module` with a recovery instruction because Terraform requires an empty target directory while the wrapper and its state lock necessarily occupy that directory. Cleanup uses a stable temporary copy of the provider helper, and Windows independently attempts both encryptions even if one cleanup step fails.
- State-wrapper hardening keeps `TFSTATE_PASSPHRASE` out of Terraform and unrelated provider subprocesses, executes helper binaries only from Terraform's canonical `delineaxpm/tss` installation tree for the lock-selected version and current Terraform platform, requires the v5 state-helper protocol before changing state, and retains the wrapper lock whenever state restoration or re-encryption is incomplete.
- The encrypted-state wrappers fail closed before decrypting when Terraform uses a named workspace, a remote backend, custom local-backend state paths, or apply/destroy state-path flags. The stock wrappers encrypt only the default local `terraform.tfstate` and backup paths; accepting another layout previously could report success while leaving the actual state file plaintext.
- An explicit empty `itemvalue` on a generated SSH file field is preserved as an attachment-deletion request instead of being replaced by the previous generated key value.
- Optional integer settings now record known zero values instead of converting an explicit `0` to null after apply, and omitted `sshkeyargs` children default to `false` instead of leaving unknown values in final state.
- Release archives now include the Terraform Registry manifest (`terraform-provider-tss_<version>_manifest.json`, listed in `SHA256SUMS`) declaring protocol `6.0`; without it the registry assumes protocol 5.0 for a provider that serves protocol 6. `.goreleaser.yml` also moves from the deprecated `archives.format` to `formats`, and the `-X main.version`/`main.commit` ldflags now target variables that exist.
- Registry docs corrected to match the schemas: `folderid`/`siteid`/`secrettemplateid` are strings, `id` is a number, `fields` is optional, `fieldname` is required, `sshkeyargs` is a single block with optional `generatepassphrase`/`generatesshkeys` (the documented `generatesshkey` never existed), the `tss_secret` data source's `id` is a string, and new pages document `tss_secret_deletion` and the `tss_secrets` ephemeral resource. The pages no longer claim to be generated by tfplugindocs; a unit test now fails when any documented attribute, type, or section drifts from the schema or when a registered type has no page.
- The live acceptance suite's deletion verifier could never reach its "secret remains discoverable" branch: the SDK re-fetches each search hit, which returned the same ambiguous 400 the verifier was corroborating. The fake-server test now exercises that branch. Verification remains fail-closed after an ambiguous failed DELETE, while a direct DELETE 404 during fixture cleanup is accepted because that request has no attachment sub-read to confuse with the target secret.
- Removed the unregistered `tss_print_secret` debug resource, which printed secret values and still compiled into release binaries.
- Creating a `tss_resource_secret` without setting `active` now creates an enabled secret. An omitted or not-yet-known value defaults to `true` on create, while updates preserve the prior state and an explicit `active = false` remains honored.
- A create that Secret Server accepted but that failed before state was recorded no longer orphans the secret silently. A partial write with a known ID and a failed post-create refresh both record the secret and template identifiers as tainted recovery state so Terraform can attempt replacement; when the backend's ambiguous absence response prevents automatic cleanup, the diagnostic now gives honest `terraform state rm` recovery guidance instead of promising that the next apply must succeed. A partial write with no usable ID, and any create failure that is not a server-sent rejection (timeout, cancellation, connection loss, or an HTTP 408/499 timeout response — where the POST may have committed after the client gave up), tell the user the secret may exist under the configured name before re-applying. A partial update reports that the write may have landed and that the next apply converges.
- Errors are no longer conflated with absence. Classic Secret Server reports deleted, never-existent, and permission-denied secrets alike as HTTP 400 `API_AccessDenied` (verified against a live tenant; it never sends 404, and Platform vaults keep recycled secrets readable with `Active=false`), so the provider distinguishes what that signal permits and is explicit about what it cannot:
  - `tss_secret_deletion` remains a one-shot operation: expected classic Secret Server 400, Platform 404, and readable recycled `Active=false` responses retain the successful deletion record without warning. A readable active secret warns but remains recorded so a restored secret is not deleted again by a later auto-approved apply. Authentication, authorization, network, and server errors fail refresh, and changing `secret_id` replaces the operation instead of merely rewriting its state without deleting the new target.
  - `tss_resource_secret`'s destroy disambiguates a failed DELETE with a follow-up read: a readable, active secret is a hard "deletion refused" error and a readable `Active=false` secret remains ambiguous because `active` is user-configurable. Every 404 also fails closed: the SDK exposes an attachment sub-request 404 with the same shape as a missing secret, and Terraform's template ID may be stale after an out-of-band template migration, so even a fileless stored template cannot prove absence. Ambiguous destroy errors give `terraform state rm` recovery guidance rather than silently dropping a possibly-live secret from state.
  - The multi-secret data source and ephemeral reads preserve exactly one result position per requested id when every secret and requested field is readable. A missing or misspelled field is a hard error, matching the single-secret path, and every secret-fetch failure aborts instead of returning a partial result (see Breaking — this replaces v4.0.x's warn-and-skip). The 400 and 404 diagnostics explain the SDK's anti-enumeration and attachment ambiguities and tell the operator how to recover.
  - Managed-secret Reads fail closed on every 404 and on classic Secret Server's access-denied absence signal, retaining state and giving `terraform state rm` recovery guidance instead of risking state loss.
  - HTTP 401/403 responses are reported as authentication or authorization failures, with expired-token and permission guidance; they are never treated as evidence that a secret is gone and never suggest removing live state.
  - The durable fix for the 400 ambiguity is upstream: tss-sdk-go parses the response body (including the `API_AccessDenied` error code) and deliberately redacts it for the secrets resource, so the provider can only classify by status class. Exposing the structured error code on `server.HTTPError` is filed as follow-up work on the SDK.
- Password fields no longer rotate on unrelated updates: both `generate = true` and configured write-only `password_value` values are suppressed unless `password_wo_version` changes, while switching from generated to explicit mode remains a real password write even when the configured version is unchanged. Explicit `password_value` now requires `password_wo_version`, preventing later write-only value changes from being invisible to Terraform. Version-only settings on creates, new fields, and existing fields are rejected before they can consume the rotation trigger without changing a password. `password_value` is rejected on non-password template fields so its value cannot round-trip into state through `itemvalue`; explicitly empty `itemvalue` is rejected on password fields as well. If Secret Server stops identifying a previously protected field as a password, refresh now fails closed instead of allowing a later refresh to persist its value. Configured `fieldname` takes precedence over a stale computed slug when a block is pointed at another template field; a stored slug is retained as fallback identity only while both the configured field name and template are unchanged. The corrected name-and-slug reference is used consistently for request construction, SSH-key preservation, and final state alignment, including server-side display-name changes. Invalid `generate=true` settings remain intact until validation so a template field that is no longer a password fails instead of being blanked.
- File-field request construction now trusts the selected template's `IsFile` metadata rather than an optional/computed plan value, treats attachment IDs strictly as server outputs instead of copying the unsupported identifier into write requests, and uses the SDK's refreshed attachment identifiers and filenames in create/read/update state instead of overwriting them with unknown or stale Terraform values. Unconfigured filenames retain their prior value during unrelated updates, while an explicitly changed filename takes precedence over stored SSH attachment metadata. Existing zero-byte attachments are omitted from unrelated updates instead of being sent as the SDK's attachment-deletion signal; renaming one requires supplying its content again. A filename the SDK would normalize by appending `.txt` is rejected before apply so the server response cannot conflict with Terraform's plan. SSH-generated values are identified by template-derived file/password flags rather than English field-name substrings.
- `sshkeyargs` is now replacement-only (ForceNew; see Breaking). Secret Server supports SSH key and passphrase generation only during creation, so changing the block recreates the secret instead of silently recording generation settings that were never sent to the server.
- Ephemeral secret values are marked sensitive as well as ephemeral, obscuring them in Terraform CLI output while retaining the existing no-state-persistence guarantee.
- The `server_url` is now validated at configure time by delinea-common's `api.NormalizeURL` — the same validator `server.New` uses — so a remote plaintext `http://` URL (and malformed URLs generally) fail plan immediately with an error naming `allow_insecure_http`, instead of mid-apply deep in the SDK with a message naming an SDK option provider users cannot set. An unknown `allow_insecure_http` value now fails configure with an attribute-named error, like the connection attributes, instead of silently resolving to `false`.
- The scheduled live acceptance workflow is now genuinely inert until the `live-tests` environment is provisioned (it previously failed every weekly run). Its gating cells explicitly pin Terraform 1.11.0 and 1.15.9 so their signals do not drift with the runner image; the separately labeled latest-release canary is deliberately unpinned and non-gating. All four workflows now share one pinned action version set — the release workflow was on the oldest pins — and the acceptance and publishing actions use Node 24 releases before GitHub removes Node 20 from hosted runners.
- The live acceptance suite now exercises the multi-secret data source, multi-secret ephemeral resource, `tss_secret_deletion` replacement, and write-only password behavior during unrelated updates. Every managed-secret case performs cancellation-bounded, backend-aware post-destroy verification: classic Secret Server's ambiguous 400 is corroborated by name search, and Platform's 404 or readable recycled `Active=false` response is accepted only after the provider's DELETE succeeded. Terraform CLI installation uses the pinned official setup action so expired OpenPGP metadata in the test harness cannot prevent pinned-version cells from starting.

### Changed

- The provider now serves its address in Terraform's canonical lowercase form, `registry.terraform.io/delineaxpm/tss`, matching the form Terraform writes to `.terraform.lock.hcl` and uses for the `.terraform/providers/` installation tree that the state-encryption wrappers search. Terraform compares provider addresses case-insensitively, so `source = "DelineaXPM/tss"`, `dev_overrides` entries, and `TF_REATTACH_PROVIDERS` keys written with the mixed-case form keep working unchanged.
- `examples/secrets/` is now one root module per directory (`examples/secrets/<name>/main.tf`) so each example can be initialized and validated on its own; the misspelled `ephemral_secret_get.tf` became `ephemeral_secret_get/main.tf`. The `vars/secrets/*.tfvars` samples are `terraform fmt`-clean and model password fields with `is_password = true` + `password_value` instead of `itemvalue`.
- Every SDK call now goes through the v3 context variants (`SecretContext`, `CreateSecretContext`, `UpdateSecretContext`, `DeleteSecretContext`, `SecretTemplateContext`, `GeneratePasswordContext`), passing Terraform's per-operation `context.Context` so plan/apply cancellation propagates to in-flight Secret Server requests. There is deliberately no whole-operation deadline — v2.0.3 had none either (its HTTP client had no timeout at all) — and each individual request remains bounded by tss-sdk-go's 60s per-request default (the provider leaves `Configuration.Timeout` unset), so operations cannot hang indefinitely.
- `README.md` and `docs/index.md` now document the v3.1.0 plaintext-HTTP rejection: `server_url` must be `https://` for any remote host; `http://` is accepted only for loopback addresses.
- Create and update reuse the secret the SDK already refreshed server-side instead of re-fetching it (one fewer GET plus attachment downloads per apply), and the multi-secret data source and ephemeral reads fetch ids concurrently (their aggregate fan-out is bounded at 8 in-flight fetches across the provider process, with order preserved) instead of strictly sequentially; a rate-limited 429 is reported distinctly with remediation guidance.
- Data-source and ephemeral field lookup now implements the documented case-insensitive matching for both display names and slugs instead of inheriting the SDK's exact-case comparison.

## [v4.0.0] - 2026-06-09

### Breaking

- Documented Terraform floor raised from 0.13 to **1.11**. `tss_resource_secret`'s new write-only password attribute requires Terraform 1.11. `README.md`, `docs/index.md`, and `examples/secrets/*.tf` (7 example configurations) updated accordingly. Users on Terraform &lt; 1.11 will see an `Unsupported Terraform Core version` error at `terraform init` once on v4.0.0.
- `itemid`, `fieldid`, `slug`, and `fielddescription` on `tss_resource_secret.fields` are now `Computed`-only (closes PBI 718755). Configurations that set any of these four attributes in `fields` blocks will fail at plan time with `Can't configure a value for X: its value will be decided automatically based on the result of applying this configuration`. These values are server-assigned by Secret Server; the previous `Optional+Computed` declaration silently accepted user input and then overwrote it. **Migration:** delete those attributes from your `fields` blocks. `fileattachmentid` remains `Optional+Computed` because it is genuinely user-settable for file-type fields.

### Security

- Bumped `google.golang.org/grpc` v1.75.1 → v1.79.3 to close [CVE-2026-33186](https://github.com/advisories/GHSA-p77j-4mvh-x3m3) (gRPC-Go authorization bypass via missing leading slash in `:path`).
- Bumped `go` directive and CI/release workflow Go version from 1.25.1 → 1.26.2 to pick up Go stdlib fixes spanning `crypto/x509`, `crypto/tls`, and `html/template` (GO-2026-4865, GO-2026-4866, GO-2026-4870, GO-2026-4946, GO-2026-4947).
- Added `.snyk` policy ignoring CVE-2026-2454 in `github.com/vmihailenco/msgpack/v5` v5.4.1. Rationale captured in the policy file: msgpack is used only inside the trusted gRPC plugin protocol with the Terraform CLI parent process; the advisory's network-input attack surface does not apply to a Terraform provider.

### Changed

- `itemvalue` is now `Sensitive: true` on the `fields` block. Defense in depth — passwords supplied via the legacy `itemvalue` path are masked in CLI output, even though the recommended path is the new `password_value` attribute.

### Fixed

- `delinea/provider.go`: corrected two malformed `log.Printf` format strings (the trailing `map[string]interface{}{...}` argument was being silently dropped) and removed an unreachable `serverConfig == nil` guard. Hygiene only — closes pre-existing `go vet` failures so the new CI workflow passes from day one.
- Provider env-var fallback now actually works (closes [gh #108](https://github.com/DelineaXPM/terraform-provider-tss/issues/108)). The provider's existing documentation promised that `TSS_SERVER_URL`, `TSS_USERNAME`, and `TSS_PASSWORD` could be set via environment variables, but the code never read them — `terraform plan` would prompt interactively for `provider.tss.password`. `Configure` now resolves each setting in the documented precedence: explicit provider attribute &gt; environment variable &gt; unset, and emits a clear plan-time error if the resulting credentials don't satisfy the auth contract (server URL is required; either username + password or token must be set; not both). `TSS_TOKEN` and `TSS_DOMAIN` env-var fallbacks added at the same time. The `server_url` provider attribute changed from `Required` to `Optional` so an env-only configuration parses; the runtime check now enforces presence after the env-var fallback runs. The framework-level `RequiredTogether` / `ExactlyOneOf` validators were removed in favor of the runtime check, since they can't see env-var-supplied values.
- `flattenSecret` block-count mismatch on partial-fields configs (`delinea/resource_secret.go`). Threaded a reference-fields list through `readSecretByID`; callers pass `plan.Fields` (Create/Update) or `state.Fields` (Read); case-insensitive match; nil reference disables filtering. Resolves "Provider produced inconsistent result after apply" (block count N → M) on configs that specify only a subset of the template's fields. Adds unit tests and three `Example_*` functions documenting the scenarios.
- Password values no longer land in `terraform.tfstate` or `terraform show -json` (PBI 700142). `flattenSecret` now writes `types.StringValue("")` for `itemvalue` when the API response indicates `IsPassword == true`; `getSecretData` routes `password_value` → API payload (with `itemvalue` as legacy fallback), and omits the field from the Update payload entirely when no new password is supplied so TSS preserves the existing server-side value. Removes a stray `FileAttachmentID = strconv.Atoi(ItemValue)` parse that could corrupt `FileAttachmentID` on numeric passwords. `alignFieldsToReference` preserves `password_wo_version` from reference (TSS does not round-trip it).
